## 1. 导航解决什么问题

可以把导航理解为五件事：

| 环节 | 通俗理解 |
| --- | --- |
| 建图 | 记录这个场地长什么样 |
| 定位 | 判断机器人现在在哪里、朝向哪里 |
| 感知 | 发现周围现在有哪些障碍 |
| 规划 | 找一条能够到达目标的路线 |
| 控制 | 持续计算该往哪走、走多快，并交给底盘执行 |

导航软件不是直接给轮子通电。它输出运动要求，电控负责执行并反馈实际状态；导航再根据传感器和反馈继续调整。路径规划和运动控制是不同环节。[Nav2 概念说明](https://docs.nav2.org/jazzy/getting_started/navigation_concepts/)

**以“从架空层一端走到另一端”为例：** 在 RViz 设置 Goal 后，导航先结合当前位置与地图规划路线，再持续计算速度，通过串口交给电控执行。行走过程中，传感器和反馈不断更新，导航据此调整。不是发出一个目标后，就让底盘不看环境地一直走。

因此，**目标已接收、路径已生成、车辆已执行、任务已完成，是四个不同阶段**。联调时说清楚卡在哪一步，比只说“导航不动了”更有帮助。

## 2. 建图与导航有什么区别

**建图是在记录环境，导航是在完成去往目标的任务。** 本项目支持边建图边导航，但日常验证通常先保存地图，再用已有地图导航。[项目建图指南](https://github.com/SMBU-PolarBear-Robotics-Team/pb2025_sentry_nav/wiki/建图指南)

本队当前常用地图名是 `louxia`，对应我们 **T8 楼下架空层的实地场地**。这是文件的名称，不代表它永远与现场一致。桌椅挪动后，实时感知需要处理变化；大范围布局改变或传感器安装改变后，应由导航人员判断是否重新标定、建图。

本部署的一套地图包含三个配套文件：

| 文件 | 用途 |
| --- | --- |
| `louxia.pgm` | 二维地图图片，描述哪些区域被占用、空闲或尚不确定 |
| `louxia.yaml` | 图片的说明，包括文件位置、尺寸换算和地图原点等 |
| `louxia.pcd` | 三维场景点云，供当前重定位方案与实时点云匹配 |

它们需要来自同一次建图、正确配套；只看到二维地图不代表重定位所需的三维地图也保存好了。操作细节见[建图和导航验证](建图和导航验证.md)。

**定位与里程计也不是一回事。** 里程计估计“刚才移动了多少、转了多少”，适合跟踪短时间运动，但误差会逐渐积累；地图定位则把当前观测与已有场地对应起来，判断“现在位于地图哪里”。重启或搬动车辆后，不能仅凭地图加载成功就认为位置正确。[ROS 坐标系约定](https://raw.githubusercontent.com/ros-infrastructure/rep/master/rep-0105.rst)

## 3. RViz 画面应该怎么看

RViz 是观察软件，不是真实世界本身。

- **地图**：之前记录的场地。
- **点云**：由雷达测量形成的空间点，反映传感器看到的环境。
- **机器人模型**：软件估计的机器人位置与姿态，不是现场照片。
- **路径**：软件准备尝试的路线，不保证车辆已经执行。
- **目标点 Goal**：希望机器人到达的位置及朝向。

判断正常，要同时看现场和画面：机器人位置、朝向合理，墙面点云与地图对应，运动时模型跟得上。仅“地图打开了”“模型不跳了”或日志出现“自动初始化”，都不足以证明定位正确。

## 4. 为什么机械安装会影响导航

软件必须知道雷达相对车体装在哪里、朝向哪里。这个位置和角度关系通常由 **TF，也就是坐标关系**描述。固定部件对应固定关系，会转动的部件需要随真实运动更新关系。[Nav2 坐标关系说明](https://docs.nav2.org/rolling/configuration_and_development/first_time_robot_setup_guide/transformation/setup_transforms/)

遇到这些名字，记住它们各自的参考对象即可，不需要背命令：

| 常见名称 | 可以怎样理解 |
| --- | --- |
| `map` | 以场地地图为参考，描述机器人在场地哪里 |
| `odom` | 用于连续跟踪短时间运动的参考坐标系 |
| `base_footprint` | 本部署中代表车体基准的坐标系 |
| `front_mid360` | 本部署使用的雷达坐标系名称，换成 MID360S 后也可以沿用 |

TF 将这些参考系联系起来，才能把“雷达看到的一个点”换算到车体或地图中。关系缺失、方向错误或更新滞后时，就可能出现点云错位、模型异常或导航等待；TF 不是控制电机转动的指令。

本队雷达装在云台上，安装倾角此前约为 30°。这不是“在软件里把点云摆正”就能处理的问题，模型与参数必须符合真实安装。

机械修改后，请告诉导航人员：

- 雷达、IMU 或云台的位置、倾角是否变化，提供尺寸或安装图。
- 支架是否松动，移动和转动时是否明显振动。
- 外壳、线束或新部件是否挡住雷达视线。
- 车体外轮廓是否变大，包括保险杠、突出件和转动部件的扫过范围。

**底盘转了，不代表雷达一定跟着转。** 云台可能在保持自身朝向；如果它相对底盘运动，导航需要真实角度反馈和正确的坐标关系，不能只靠 RViz 模型“看起来在转”。

## 5. 电控与导航怎样配合

最需要对齐的是：指令含义、参考方向、单位、控制模式与反馈。

| 需要确认 | 为什么重要 |
| --- | --- |
| 前后、左右、旋转分别是什么方向 | 方向理解不一致会造成反向或侧向运动 |
| 指令以底盘、云台还是场地为参考 | 同一组数值在不同参考系下可能表示不同运动 |
| 速度、角速度和角度的单位 | 角度目标与转动速度不能混用 |
| 自动导航、遥控和跟随模式谁优先 | 避免两套指令同时争夺控制权 |
| 是否使能、真实速度和角度反馈 | 区分“软件要求动”和“实际已经动” |
| 断连、指令超时和接管后怎么停止 | 不能持续执行过期的运动要求；这项需现场验收 |

ROS 常见约定是 x 向前、y 向左、z 向上，距离用米、角度用弧度；线速度通常是米/秒，角速度是弧度/秒。但下位机协议必须逐项确认，不能假定自动一致。[ROS 单位与坐标约定](https://raw.githubusercontent.com/ros-infrastructure/rep/master/rep-0103.rst)

**命令速度不等于实际速度。** 地面打滑、限速、未使能、通信断开都可能使实际运动与要求不同，反馈能帮助各组定位问题。

## 6. 为什么有地图还会撞障碍

地图不是实时、无盲区的环境保证。薄桌腿、低矮物体、遮挡、测量特性和处理范围，都可能影响障碍检测。

导航常用“代价地图”综合已知场地和实时障碍：全局地图帮助选路线，局部地图帮助处理车旁情况。[Nav2 环境表示](https://docs.nav2.org/rolling/getting_started/navigation_concepts/environmental_representation/)

两个容易混淆的概念：

- **车体轮廓**：告诉软件机器人真实占多大地方。本队底盘此前提供的尺寸为长 60 cm、宽 45 cm，实际仍要计入突出件和旋转时的占用范围，不能把机器人当成一个点。[车体轮廓说明](https://docs.nav2.org/rolling/configuration_and_development/first_time_robot_setup_guide/footprint/setup_footprint/)
- **膨胀区域**：提高障碍附近的通行代价，帮助规划尽量留出距离。它不是所有彩色区域都绝对禁止通行，也不是自动检测盲区障碍的能力。[膨胀层说明](https://docs.nav2.org/rolling/configuration_and_development/configuration_guide/core_servers/costmap_2d/costmap_plugins/inflation/)

所以，不应只为了画面好看而减小避障范围，也不能认为“调大膨胀半径就一定不撞”。安装视野、定位、轮廓、速度和制动表现需要一起验证；旋转扫描也不能代替可靠的障碍检测与停止机制。

**重新规划与后退有什么区别？** 重新规划是根据当前情况重新计算路线，目标可以不变；后退、等待等则可能是受阻后的恢复动作，具体取决于当前配置。正常绕开障碍不一定需要后退，更不是“先撞上再退”。若反复前进、后退却没有进展，应检查感知、定位、通道宽度和执行反馈，而不是不断重复发 Goal。[Nav2 规划与恢复流程](https://docs.nav2.org/jazzy/getting_started/nav2_behavior_trees/detailed_behavior_tree_walkthrough/detailed_behavior_tree_walkthrough/)

## 7. 联调时各组提供什么

| 参与者 | 重点提供或确认 |
| --- | --- |
| 机械 | 实际外形尺寸、传感器安装关系、运动范围、固定可靠性和视野遮挡 |
| 电控 | 协议与单位、控制参考系、模式切换、实际反馈、通信状态与停止行为 |
| 导航 | 地图版本、定位是否正确、计划路线、速度输出、坐标关系和异常日志 |
| 现场测试人员 | 环境是否安全、接管方式是否可用、真实车辆表现与测试记录 |

遇到问题先描述现象，不急着归因：

| 现象 | 优先一起确认什么，而不是直接下结论 |
| --- | --- |
| 点 Goal 不动 | 目标是否被接收、是否输出速度、串口是否连接、底盘是否使能 |
| 车在动，模型不跟随 | 传感器、里程计、坐标关系和显示数据是否持续更新 |
| 地图和点云错位 | 地图是否选对、定位是否正确、安装与反馈是否发生变化 |
| 只有底盘转，云台不转 | 电控模式、云台控制来源，以及实际反馈，不能只改显示模型 |
| 碰撞或绕不开障碍 | 障碍是否被看到、车体轮廓是否准确、速度和停止距离是否合理 |

反馈问题时最好一起给出：发生时间、地图名、当时操作、现场视频、RViz 截图和终端报错。这样能把现象与程序日志对应起来。

## 8. 实验前记住四件事

1. 先确认定位正确，再发送目标；从低速、短距离、空旷区域开始验证。
2. 有人负责接管，周围保持安全距离，停止手段要提前验收。
3. 出现危险用现场接管/急停，不能把关终端当成硬件急停。
4. 一次到达目标不代表整车已经完成避障和可靠性验收；机械或电控改动后要复验受影响的部分。

需要动手时，先看[导航过程](导航过程.md)；需要更换场地地图时，再看[建图和导航验证](建图和导航验证.md)。两页顶部均有 TXT 下载链接。详细算法和排错命令留给“导航新人培训”栏目，不要求电控、机械队员在这里掌握。

本文中的设备尺寸、安装位置和地图名来自本队已有沟通，现场变更后应同步更新。官方文档链接用于解释通用概念，不要求把链接中的新版 Nav2 参数直接套用到本队 Humble 部署。

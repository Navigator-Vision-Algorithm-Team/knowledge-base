# 北京理工大学追梦战队哨兵自主导航

## 项目概览

| 项目 | 内容 |
|---|---|
| 仓库 | [Walker152/navi_minco_bit](https://github.com/Walker152/navi_minco_bit) |
| 定位与重定位 | 双 Livox MID-360、Point-LIO、GICP |
| 环境感知 | ROGMap、地形语义投影、Signed ESDF |
| 规划与控制 | Nav2、全局搜索、MINCO、SE(2) MPC |
| 决策 | BehaviorTree.CPP v3、裁判系统与底盘通信 |
| 基线环境 | Ubuntu 22.04、ROS 2 Humble、全向底盘 |
| 许可证 | [Apache License 2.0](https://github.com/Walker152/navi_minco_bit/blob/master/LICENSE) |

`navi_minco_bit` 是北京理工大学追梦战队面向 RoboMaster 2026 赛季开发的 ROS 2 哨兵自主导航工程，覆盖从双激光雷达输入、定位与重定位、在线地图，到连续轨迹规划、MPC 跟踪和比赛决策的完整链路。项目介绍见 [RoboMaster 社区开源帖](https://bbs.robomaster.com/article/1940848?source=1)。

项目团队说明，感知—规划—控制主线主要参考并复现了中国科学技术大学 RoboWalker 2025 哨兵导航方案，再结合自身双雷达、全向底盘、ROS 2 系统和比赛策略进行了工程化修改。因此更适合用于理解完整系统的连接方式、实车配置和改造思路，而不应被视为无需适配即可部署的通用软件包。

## 系统链路

```text
双 Livox MID-360
        │
        ▼
驱动侧时间配对、外参变换与点云融合
        │
        ▼
Point-LIO ──── GICP + 预建 PCD
        │          │
        ▼          ▼
     ROGMap     map 坐标系重定位
        │
        ▼
地形语义投影 + Signed ESDF
        │
        ▼
全局搜索 + MINCO 连续轨迹优化
        │
        ▼
SE(2) MPC ──── BehaviorTree + Nav2
        │
        ▼
      全向底盘
```

仓库还提供 `pcd_trans` 预建地图处理工具和 `dual_lidar_calibration` 双雷达离线外参标定工具，可用于补齐建图、标定和上线前的数据准备环节。

## 主要技术内容

### 1. 双雷达驱动侧融合与离线标定

实车使用两台 Livox MID-360。修改后的 `livox_ros_driver2` 可在 Driver 内完成时间配对、后雷达到前雷达的外参变换和点云合并，并保留单雷达、双雷达两套启动配置。Driver 与 Point-LIO 支持 ROS 2 Component 和进程内通信，以减少大点云的序列化与复制开销。

`dual_lidar_calibration` 可以读取 ROS 2 bag，利用两台雷达的点云和 IMU 数据离线估计外参。雷达重新安装或机械位置变化后应重新采集数据并标定，不能沿用仓库中的实车外参。

### 2. Point-LIO 与 GICP 重定位

Point-LIO 同时承担高频状态估计和稠密去畸变点云输出。项目将定位更新、里程计、完整点云和可视化地图的发布频率解耦，使状态估计可以维持较高频率，而 ROGMap 按自身处理能力消费完整点云。

Point-LIO 启动后使用自身的 `camera_init` 世界坐标系；GICP 重定位模块通过预建 PCD 与在线稠密点云配准，估计 `map → camera_init` 变换。这样，LIO 可以继续在局部世界系工作，Nav2、行为树、巡逻点和比赛语义则保持在固定的 `map` 坐标系中。

### 3. ROGMap、地形语义与动态遗忘

ROGMap 维护滑动三维概率占据地图，并通过 `ProjectionLayer` 将同一 XY 栅格内的占据数量、高度范围、跨度和垂直占据率压缩为四类二维语义：

- `FREE`：空闲；
- `PASSABLE`：可通行；
- `OCCUPIED`：占据；
- `UNKNOWN`：未知。

在此基础上生成的 Signed ESDF 向搜索、MINCO、安全检查和恢复模块提供障碍内外的连续距离与梯度查询。动态目标目前主要依靠概率占据和时间衰减清除残影，仓库中的实验性点云聚类默认没有启用。

### 4. PRIORMAP / EXPLORATION 双模式规划

规划器实现为 Nav2 Planner Plugin，提供两种模式：

| 模式 | 用途 |
|---|---|
| `PRIORMAP` | 使用 Nav2 先验地图完成全局引导，ROGMap 提供局部在线障碍和 ESDF 约束；这是团队当前的比赛基线 |
| `EXPLORATION` | 不依赖完整先验地图，在 ROGMap 当前有效区域内搜索和规划 |

前端通过 A* / SMAC 风格搜索得到离散路径，再进行局部截取、边界裁剪、视线稀疏化、转角速度分配和时间初始化，最后由 MINCO 联合优化中间控制点与各段持续时间。优化完成后还有独立的 Safety Gate 检查速度、加速度、终点和 ESDF 安全距离。

### 5. SE(2) MPC 与安全恢复

控制器针对全向底盘设计，状态为 `[x, y, yaw]`，控制量为 `[vx, vy, wz]`，使用 qpOASES 求解约束 QP。控制链路处理速度与加速度限制、控制延迟、雷达到底盘中心的杆臂偏置、速度死区、Nav2 Speed Limit 和小陀螺状态。

Planner 和 Controller 约定使用全局世界坐标系的平移速度，底盘通信层再依据当前 yaw 转换为底盘运动指令。迁移时必须确认本队底盘接口采用相同约定，否则可能出现速度方向随车体朝向错误旋转的问题。

### 6. 比赛行为树

比赛决策使用 BehaviorTree.CPP v3。Blackboard 汇集裁判系统、机器人、导航和人工控制状态，行为树再按优先级选择导航、巡逻、姿态、资源或恢复行为，并向 Nav2 和通信模块下发指令。

当前全局策略以 `Balance`、`Offensive` 和 `Defend` 三类模式为主，通过比赛时间、血量、弹量、前哨站和基地状态等人工条件切换。不同模式可以选择不同的 `PatrolList`，从而将“是否巡逻”与“巡逻哪些点”分开维护。

## 团队公开的实车基线

| 项目 | 配置 |
|---|---|
| 计算平台 | Intel NUC 13、Core i5-1340P、32 GB RAM |
| 激光雷达 | 2 × Livox MID-360，驱动侧融合 |
| ROGMap | 0.05 m 分辨率，10 × 10 × 1.5 m 滑动窗口 |
| 规划 | `PRIORMAP`，20 Hz MINCO 优化配置 |
| 控制 | 100 Hz Nav2 Controller Server，MPC 预测时域 0.5 s |

这些参数是项目团队当前车辆的基线，不是不同计算平台、雷达布局或底盘上的性能保证。

## 环境与构建入口

项目需要 Ubuntu 22.04、ROS 2 Humble、C++17、Livox-SDK2，以及 Nav2、BehaviorTree.CPP v3、PCL、Eigen3、OpenMP、yaml-cpp、glog 和 fmt 等依赖。README 当前给出的构建入口指定 `rog_map_work` 分支：

```bash
git clone --branch rog_map_work --single-branch \
  https://github.com/Walker152/navi_minco_bit.git ~/2025-sentry-navi
cd ~/2025-sentry-navi
source /opt/ros/humble/setup.bash
./build.bash
source install/setup.bash
```

`start.bash` 当前绑定 `~/2025-sentry-navi`，并会打开多个 GNOME Terminal、执行 PTP 相关命令和录制 rosbag，更适合实车桌面环境。用于无界面服务器或不同工作空间路径时，应先修改脚本。

## 使用边界与待完善项

- 仓库包含特定车辆的主机与雷达 IP、双雷达外参、TF 偏置、地图原点、巡逻点和比赛参数，上车前必须逐项重新配置。
- 当前地形投影尚未完整解决高台边缘、断崖、无支撑区域等负障碍问题。
- 动态机器人目前主要依靠占据衰减处理，尚未形成稳定的显式动态目标分割、速度估计和未来轨迹预测链路。
- MINCO 以 ESDF 软代价配合离散安全检查为主，开源者仍计划研究硬约束或安全走廊；原帖也说明部分 Safety Gate 执行问题尚未完项。
- Planner 和 MPC 主要面向全向底盘；差速、Ackermann 等非完整约束底盘需要重新设计搜索、轨迹约束和控制模型。
- 高层战术仍以人工规则和优先级为主。LLM 或其他智能策略仅是后续设想，并非当前仓库已经提供的功能。
- `package.xml` 可能没有覆盖全部系统依赖，执行 `rosdep` 后仍可能需要根据构建报错补装系统库。
